# Detection Scenarios

## 1. Overview

This document describes the controlled security testing scenarios performed against the monitored Ubuntu Web Server.

The objective is to validate the Wazuh SIEM monitoring pipeline by generating realistic security events and verifying that they are detected and presented as security alerts.

Two scenarios were tested:

1. Web reconnaissance and scanning using Nikto
2. Web login brute-force simulation using Hydra

The testing workflow follows a basic SOC monitoring process:

```text
Attack Activity
      │
      ▼
Target Web Server
      │
      ▼
Log Generation
      │
      ▼
Wazuh Agent
      │
      ▼
Wazuh Manager
      │
      ▼
Detection Rule
      │
      ▼
Security Alert
      │
      ▼
SOC Investigation
```

All tests were performed in a controlled laboratory environment against systems under the project's control.

# 2. Detection Scenario 1 — Web Scanning with Nikto

## 2.1 Objective

The first scenario simulates web reconnaissance and scanning activity against the monitored Ubuntu Web Server.

Nikto was used to generate a large number of HTTP requests and identify potentially interesting web resources and server information.

The objective was to verify whether Wazuh could detect abnormal HTTP activity generated by the scan.

---

## 2.2 Attack Flow

The simplified attack flow is:

```text
┌──────────────────┐
│    Kali Linux    │
│                  │
│      Nikto       │
└────────┬─────────┘
         │
         │ HTTP Requests
         ▼
┌──────────────────┐
│ Ubuntu Web Server│
│                  │
│ Apache / WordPress│
└────────┬─────────┘
         │
         │ Apache Logs
         ▼
┌──────────────────┐
│   Wazuh Agent    │
└────────┬─────────┘
         │
         │ Security Events
         ▼
┌──────────────────┐
│  Wazuh Manager   │
│                  │
│ Detection Rules  │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Security Alert   │
└──────────────────┘
```

---

## 2.3 Testing Activity

Nikto was executed from the Kali Linux testing system against the monitored Web Server.

The scan generated repeated HTTP GET requests against the web application.

The purpose of the activity was not to exploit the target system, but to generate controlled reconnaissance traffic for SIEM detection validation.

---

## 2.4 Detection Result

Wazuh detected abnormal HTTP activity generated during the scan.

The observed detection was associated with:

```text
Rule ID: 31101
Level: 5/10
Activity: Abnormal HTTP GET Requests
```

The alert was visible through the Wazuh Dashboard.

The detection demonstrates that web server activity can be collected and analyzed centrally by Wazuh.

---

## 2.5 Investigation

From a SOC Tier 1 perspective, the alert can be investigated using the following information:

| Investigation Field | Purpose |
|---|---|
| Source IP | Identify the system generating the traffic |
| Destination IP | Identify the targeted endpoint |
| Timestamp | Establish when the activity occurred |
| HTTP Method | Determine the request type |
| Requested URI | Identify accessed resources |
| Rule ID | Identify the Wazuh detection rule |
| Alert Level | Determine the initial severity |

The analyst can correlate the alert timestamp with Apache access logs to validate that the HTTP activity originated from the testing system.

---

## 2.6 SOC Interpretation

The detected activity is consistent with web reconnaissance.

A SOC analyst should consider:

- Is the source IP authorized?
- Was the scanning activity expected?
- Which web resources were accessed?
- Were there repeated or unusual requests?
- Did the activity progress to exploitation attempts?
- Are additional alerts associated with the same source?

In this laboratory, the source was an authorized Kali Linux testing system.

Therefore, the alert represents a successful detection validation rather than a real security incident.

# 3. Detection Scenario 2 — WordPress Brute Force with Hydra

## 3.1 Objective

The second scenario simulates repeated login attempts against the WordPress login endpoint.

Hydra was used from Kali Linux to generate repeated authentication requests against:

```text
/wp-login.php
```

The objective was to verify whether Wazuh could identify the repeated HTTP POST activity associated with a brute-force login attempt.

---

## 3.2 Attack Flow

The simplified attack flow is:

```text
┌──────────────────┐
│    Kali Linux    │
│                  │
│      Hydra       │
└────────┬─────────┘
         │
         │ Repeated HTTP POST
         ▼
┌──────────────────┐
│ Ubuntu Web Server│
│                  │
│ WordPress        │
│ /wp-login.php    │
└────────┬─────────┘
         │
         │ Application / Web Logs
         ▼
┌──────────────────┐
│   Wazuh Agent    │
└────────┬─────────┘
         │
         │ Security Events
         ▼
┌──────────────────┐
│  Wazuh Manager   │
│                  │
│ Detection Rules  │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ High-Level Alert │
└──────────────────┘
```

---

## 3.3 Testing Activity

Hydra was executed from the Kali Linux testing system to generate repeated login requests against the WordPress authentication endpoint.

The target endpoint was:

```text
/wp-login.php
```

The repeated authentication attempts generated HTTP POST requests that were observed by the monitored Web Server.

---

## 3.4 Detection Result

Wazuh detected the repeated HTTP POST activity associated with the brute-force simulation.

The observed detection was associated with:

```text
Rule ID: 40501
Level: 10/10
Activity: Repeated HTTP POST Requests
Target: /wp-login.php
```

The alert was visible through the Wazuh Dashboard.

The high alert level demonstrates that the event was treated as a significant security event within the laboratory monitoring environment.

---

## 3.5 Investigation

A SOC Tier 1 analyst can investigate the alert using:

| Investigation Field | Purpose |
|---|---|
| Source IP | Identify the system generating authentication attempts |
| Destination IP | Identify the targeted Web Server |
| Timestamp | Determine the attack period |
| HTTP Method | Confirm repeated POST activity |
| Requested URI | Confirm the targeted login endpoint |
| Rule ID | Identify the detection rule |
| Alert Level | Assess the initial severity |
| Event Frequency | Determine whether the activity is repetitive |

The analyst can correlate the Wazuh alert with Web Server logs to confirm the repeated requests.

---

## 3.6 SOC Interpretation

Repeated login attempts against an authentication endpoint may indicate brute-force activity.

A SOC analyst should investigate:

- Whether the source IP belongs to an authorized user or system
- The number and frequency of authentication attempts
- Whether the targeted account exists
- Whether authentication attempts were successful
- Whether other services were targeted by the same source
- Whether additional security alerts occurred during the same time period

In this laboratory, the activity was intentionally generated using Hydra.

Therefore, the event represents a controlled detection test.

# 4. Detection Comparison

The two scenarios demonstrate different types of suspicious web activity.

| Scenario | Tool | Target | Activity | Rule ID | Level |
|---|---|---|---|---|---|
| Web Scanning | Nikto | Web Server | Abnormal HTTP GET requests | 31101 | 5/10 |
| Web Login Brute Force | Hydra | `/wp-login.php` | Repeated HTTP POST requests | 40501 | 10/10 |

The results demonstrate that Wazuh can distinguish between different security events based on the characteristics of the observed activity.

# 5. SOC Investigation Workflow

The detection scenarios can be mapped to a simplified SOC Tier 1 workflow.

```text
1. Alert Generated
        │
        ▼
2. Initial Triage
        │
        ▼
3. Identify Source and Target
        │
        ▼
4. Analyze Event Details
        │
        ▼
5. Correlate with Logs
        │
        ▼
6. Determine False Positive / True Positive
        │
        ▼
7. Escalate or Close
```

### Step 1 — Alert Generated

Wazuh generates an alert after matching observed activity against its detection rules.

### Step 2 — Initial Triage

The analyst reviews:

- Alert level
- Rule ID
- Timestamp
- Source
- Destination
- Event type

### Step 3 — Identify Source and Target

The analyst determines which system generated the activity and which endpoint was targeted.

### Step 4 — Analyze Event Details

The analyst reviews the HTTP method, URI, request frequency, and other available event information.

### Step 5 — Correlate with Logs

The Wazuh event can be compared with the Web Server logs to validate the observed activity.

### Step 6 — Determine Classification

The analyst determines whether the activity is:

- Benign
- Expected security testing
- False positive
- Suspicious activity
- Confirmed malicious activity

### Step 7 — Escalation or Closure

For a real environment, confirmed suspicious activity may be escalated to a higher SOC tier or incident response team.

In this laboratory, both events were intentionally generated and can therefore be classified as controlled security tests.

# 8. Lessons Learned

The testing process demonstrated several practical security monitoring concepts:

- Endpoint logs are valuable sources of security telemetry.
- Centralized log collection simplifies security monitoring.
- Detection rules provide an initial signal for SOC investigation.
- Alert severity helps prioritize analyst attention.
- Source and destination information are important during triage.
- Log correlation is necessary to understand the context of an alert.
- Security alerts should not automatically be treated as confirmed incidents.
- Controlled attack simulations are useful for validating SIEM deployments.

The project also highlights the importance of moving beyond simple alert generation toward structured investigation and incident response workflows.

---

# 9. Limitations

This laboratory focuses on basic detection validation and does not represent a complete production SOC environment.

Current limitations include:

- Small number of monitored endpoints
- Limited attack scenarios
- No automated incident response
- No SOAR integration
- No threat intelligence enrichment
- No long-term security analytics
- No formal incident ticketing workflow
- No high-availability Wazuh architecture

These limitations provide opportunities for future development.
